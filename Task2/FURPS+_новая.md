| Код | Требования                         | Комментарий  |
|-----|------------------------------------|--------------|
| F   | Функциональные (Functionality)     |              |
| F1  | Сайтом банка могут пользоваться незарегистрированные пользователи, у них должна быть возможность оставить заявку на депозит, указав ФИО и телефон. | |
| F2  | Сотрудники кол-центра должны иметь возможность обработать заявку пользователя в системе кол-центра и отправить заявку со специальными условиями в сервис депозитов. | Такая же возможность должна быть и у партнерского кол-центра. |
| F3  | Сайт и интернет-банк должны обеспечивать шифрование трафика между клиентом и сайтом/интернет-банком, а также между системами. | |
| F4  | Интернет-банком могут пользоваться только зарегистрированные пользователи (не новые). | |
| F5  | Интернет-банк должен иметь возможность предоставлять список доступных депозитов с актуальными ставками и персонализированные ставки лично для клиента. | |
| F6  | Интернет-банк должен иметь возможность принять заявку пользователя на открытие депозита после выбора счета и ввода суммы. Операция должна быть подтверждена СМС-кодом. | |
| F7  | Сервис ставок должен позволять сотрудникам бэк-офисов депозитов и кредитов вести ставки (вместо XLS) и хранить их в собственной БД. | С этими данными должны работать сотрудники депозитного и кредитного отделов. У них не должно быть доступа к данным друг друга. |
| F8  | Сервис депозитов должен поддерживать автоматизированный процесс согласования ставки по заявке. | Вне MVP / целевое состояние — автоматизированное заведение заявок на депозит. В MVP заявку обрабатывает менеджер вручную (см. F9). |
| F9  | В MVP заявку на депозит обрабатывает менеджер бэк-офиса в сервисе депозитов. Клиент после обработки получает СМС-оповещение: сначала о финальной ставке, потом об открытом депозите. Сервис депозитов обновляет статус заявки после ручных операций | |
| F10 | Пользователь проходит идентификацию офлайн в офисе — в системе такой функционал не предусмотрен. | |
| U   | Удобство использования (Usability) |              |
| U1  | Интерфейс сайта и интернет-банка должен соответствовать системе дизайна компании — иметь привычные цвета и брендинговые элементы. | |
| R   | Надёжность (Reliability)           |              |
| R1  | Доступность платформы 99.9%. | |
| R2  | Режим работы 24/7. | Для обеспечения этого требования необходимо поддержать аппаратную возможность быстрого переключения трафика на резервный ЦОД. Резервный ЦОД должен выдерживать нагрузку основного ЦОД, механизм деградации не предусмотрен. |
| P   | Производительность (Performance)   |              |
| P1  | Отклик по всем синхронным операциям < 300 мс. | |
| P2  | Должна быть предусмотрена поддержка горизонтального масштабирования всех новых компонентов системы, включая мощности ЦОД, с балансировкой трафика. | |
| S   | Поддерживаемость (Supportability)  |              |
| S1  | Должна быть разработана документация для дальнейшего расширения. | |
| S2  | Должна быть поддержка интеграционного тестирования. | |
| +R  | + Ограничения (Restrictions)       |              |
| +R1 | Интернет-банк. Клиент-серверная система на веб-фреймворке ASP.NET MVC 4.5 на основе .NET Framework 4.5 и СУБД MS SQL. | Интернет-банк в текущем виде несовместим с Kafka. |
| +R2 | Сайт — PHP и React.js. | |
| +R3 | Система кол-центра (Java Spring Boot, React, PostgreSQL), поддерживается подрядчиком. | |
| +R4 | Автоматизированная банковская система (АБС). Интерфейс пользователей — это десктопный клиент на Delphi и СУБД на Oracle. Основная логика работы системы реализована процедурами на PL-SQL в СУБД. | Основная логика — процедуры, нет возможности горизонтально масштабировать. |
| +R5 | Принцип выбора технологий: технологии должны быть совместимы с существующими платформами разработки, а в команде должна быть экспертиза: БД: Oracle, MS SQL; очереди: Kafka; код: Java, .NET. | |
| +R6 | Новую функциональность добавляем в микросервисной архитектуре с развертыванием в Kubernetes в рамках MVP с депозитами. | Сейчас основная логика находится в процедурной системе, которая может масштабироваться только вертикально. Для обеспечения требований нам нужно не добавлять новую логику напрямую в АБС, а вынести часть для работы с депозитами в рамках MVP с отдельной базой для поддержки горизонтального масштабирования. |
| +R7 | Для разработки бэкенда можно использовать Java и Spring Boot. | |
| +R8 | Интернет-банк не должен работать напрямую с API АБС — взаимодействие через очередь или события для защиты перегруженной БД. | |
| +R9 | Система должна иметь отдельный от ядра интернет-банка СМС-функционал. | Так как ядро интернет-банка трогать нежелательно, нужна новая система, реализованная силами команды IT-отдела банка. |
| +R10 | Шифрование трафика: TLS не ниже 1.2 для всех каналов (клиент – сайт/интернет-банк, межсервисное и межсистемное взаимодействие, Kafka, соединения с БД). Между внутренними сервисами и с внешними системами — взаимный TLS. | Интернет-банк на .NET Framework 4.5 требует явной настройки TLS 1.2. |
| +R11 | Сервис депозитов — источник истины по депозитам и статусам заявок; данные хранятся в его собственной БД. | Решение принято для разгрузки БД АБС (см. +R6). |
| +R12 | Интеграция (адаптер) сервиса депозитов с АБС в MVP не реализуется. | Если АБС потребуются данные о депозите, она получает их по запросу через очередь, без прямого доступа к БД сервиса депозитов. |
| +R13 | Система кол-центра должна вместо АБС начать писать заявки в Kafka. | Согласуется с +R5 (экспертиза в Kafka) и +R8 (защита перегруженной БД АБС от прямых обращений). |
